# Technology selection and rationale

Status: proposed selections for the Python platform. These are design choices, not claims that the corresponding services or packages have been wired into the ISO.

| Concern | Selection | Why and tradeoff |
| --- | --- | --- |
| Live distribution and ISO builder | Existing Debian 13 x86_64 `live-build`, ISO hybrid, Syslinux BIOS and GRUB UEFI | Reuses the current build, package list, isolation hook, menus, and validation. Debian's [live-build manual](https://live-team.pages.debian.net/live-manual/html/live-manual.en.html) documents the layout. Actual build and both boot paths still need Linux/QEMU and R240 tests. Byte-identical builds require a pinned package snapshot. |
| Language | Python 3 from Debian packages | Meets the requested language, provides JSON/SQLite/HTTP libraries, and supports fixture-based testing. Keep Bash checks working until Python health parity is proven; the current Python CLI covers only inventory and limited SMART. |
| Redfish client | Python `requests` with explicit resource/action discovery | Small, readable synchronous client for one-target state transitions; bounded retries and timeouts are easier to audit. Use standard Redfish resources first and a narrow Dell OEM adapter only where firmware requires it. Dell publishes [Python examples](https://github.com/dell/iDRAC-Redfish-Scripting) and [iDRAC 9 API guidance](https://dl.dell.com/topicspdf/idrac9-lifecycle-controller-v4x-series_api-guide_en-us.pdf). |
| Target inventory | PyYAML `safe_load` plus explicit validation | Allows the requested `server-list.yaml` without executable config. Only target metadata and secret references belong in it. Debian has a [python3-yaml package](https://packages.debian.org/stable/python/python3-yaml). |
| Report format | Versioned JSON schema plus derived plain text | JSON supports automation and exact per-check evidence; text remains useful on tty1 and through BMC. Keep health verdict separate from collection/run status, and never silently drop unsupported sensors. |
| Live and controller HTTP service | Python `aiohttp`, HTTPS at the controller edge | One library can serve read-only live results and receive reports on the controller. Debian 13 ships [python3-aiohttp](https://packages.debian.org/trixie/python3-aiohttp). The controller's authenticated persisted API is primary; a live host endpoint is optional because host networking may be unavailable. TLS, authentication, size limits, and bind address require explicit configuration. |
| Controller state store | SQLite initially; report files by run ID and hash | Transactions and unique constraints make run transitions restart-safe without an external database for a single controller. Reassess PostgreSQL only when fleet concurrency or multi-controller deployment requires it. SQLite is not the report archive by itself. |
| ISO publication | Existing HTTP(S) server with immutable, checksum-identified ISO URL | iDRAC fetches the image directly; the controller does not stream ISO bytes through Redfish. Verify insertion by reading iDRAC state. Dell documents firmware-dependent [virtual-media behavior](https://www.dell.com/support/kbdoc/en-ca/000185550/idrac-virtual-media-troubleshooting). |
| Agent delivery | HTTPS upload with run-scoped credential, local RAM/approved-USB copy first | The optical ISO cannot store results. Controller acknowledgement permits safe later cleanup; network loss leaves a console/USB recovery path. A short-lived per-run credential requires a tested run-specific bootstrap delivery mechanism. |
| Vendor RAID utilities | Existing optional local `storcli`/`perccli`/`ssacli` mechanism | Preserves licensing boundaries. Redfish inventory is the default PERC view; no proprietary binary is fetched or redistributed by the build. |

## Redfish compatibility policy

Do not assume `/redfish/v1/Managers/iDRAC.Embedded.1/VirtualMedia/CD` exists on every iDRAC 9 release. Discover links and action targets from the service root and manager/system resources. Dell's virtual-media example documents `CD`/`RemovableDisk` IDs on older firmware and indexed devices on newer firmware; newer APIs may place virtual media under the system. [Dell scripting implementation](https://github.com/dell/iDRAC-Redfish-Scripting/blob/master/Redfish%20Python/InsertEjectVirtualMediaREDFISH.py). Likewise, inspect `BootSourceOverrideTarget@Redfish.AllowableValues` before using `Cd`; Redfish defines `Once` as a single subsequent boot, after which the override is disabled. [DMTF Redfish resource guide](https://redfish.dmtf.org/schemas/v1/DSP2046_2025.2.html).

Use only GET for health inventory and logs. The deployment writer allows these specific actions: insert/eject virtual media, set one-time boot, and request a graceful system reset or power-on. Never call Redfish storage, firmware update, BIOS configuration, secure erase, or persistent boot-order actions from the health workflow. A Redfish response that lacks a resource or sensor is recorded as unsupported/unavailable, not as a failed component.

## Network and security decisions

- The ISO currently masks network management services. A future orchestration profile must deliberately enable a specified diagnostic NIC and DHCP/static configuration. `diag.network=yes` currently enables a **network inventory check only**; it is not transport configuration. No design should imply remote collection works before this is changed and validated.
- Use iDRAC TLS certificate validation by default. Internal CA roots can be configured; insecure TLS must be a conspicuous lab-only override. Redfish credentials reside in a secret provider or process environment, never in `server-list.yaml`, an ISO, or command-line arguments captured by process listings.
- The run-specific ISO bootstrap may contain a short-lived enrollment credential. Serving that image makes the credential available to anyone with download access; use restricted publication, a single-run token, expiry, and report identity checks. Do not embed a fleet-wide secret in a reusable image.
- Host-side HTTP visibility requires a designated diagnostic network. The controller API is the durable retrieval endpoint. If host networking fails, leave the server at a shell and keep the local report; do not claim that an iDRAC-mounted ISO automatically supplies a data channel back to the controller.
- The controller may restart a server during an authorised diagnostic deployment, which interrupts any installed OS workload. Preflight, maintenance scheduling, and precise target identity are therefore required before the one-click action is enabled.

## Decisions deferred until the R240 trial

The exact iDRAC virtual-media slot, boot-mode setting, license behavior, and result-network path must be observed on the lab R240. The per-run bootstrap delivery method must preserve BIOS and UEFI bootability and pass checksum validation. An optional direct live-host HTTP server and return-to-disk automation remain disabled until report durability and media handoff are proven. These are explicit release gates rather than assumed features.
