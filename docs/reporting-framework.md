# Increment 4: reporting framework

## Architecture review

The live ISO currently launches `server-check.sh`, which runs a fixed allowlist of read-only Bash checks. Each Bash check prints raw evidence and an `INFO`, `OK`, `WARNING`, or `FAIL` verdict. The launcher already isolates check failures and writes a uniquely named raw evidence report. Its console summary is useful to a technician but was not a stable machine-readable contract. The older `src/server_check/cli.py` remains a separate Python inventory interface with a different JSON shape; it is not the ISO's health runner.

The new reporting layer extends that boot path. It does not change SMART, EDAC, RAID, sensor, or kernel-error logic. The Bash launcher passes the final verdict and completion timestamp for each selected check to a Python adapter. The adapter reads the check's raw section, converts it to a `CheckResult`, and preserves the entire section in `details.raw_evidence`.

```mermaid
flowchart LR
    B[Bash checks] --> L[Existing launcher]
    L --> R[Raw evidence report]
    L --> A[Python legacy adapter]
    R --> A
    A --> M[CheckResult / ServerReport]
    M --> J[JSON renderer]
    M --> T[Text renderer]
    J --> S[Local report sink]
    T --> S
    S --> P[/reports/report.json and report.txt]
```

## Reporting contract

Every normalized check has `name`, `status`, `summary`, `details`, and a UTC `timestamp`. `status` is exactly `PASS`, `WARN`, or `FAIL`. The report adds `schema_version`, `hostname`, `serial`, `overall_status`, `generated_at`, and the `checks` list. Overall status is `FAIL` if any check fails, otherwise `WARN` if any check warns, otherwise `PASS`. An empty selection is `WARN` because it cannot establish health.

Legacy `OK` maps to `PASS`, `WARNING` to `WARN`, and `FAIL` to `FAIL`. An inventory-only `INFO` maps to `PASS` only when evidence was collected; the summary states that inventory is not a health claim. An `INFO` from a health check or an unavailable inventory utility maps to `WARN`. Missing captured evidence also maps to `WARN`. This keeps unavailable coverage distinct from an explicit hardware failure within the required three-status format. The original source verdict remains in `details.source_verdict`.

`CheckResult` and `ServerReport` live in `src/server_check/reporting/model.py`; renderers and sinks import the model but no diagnostic check module. The `ReportSink` protocol accepts one rendered report, so a later HTTP, Redfish, or SMB transport can be added without changing checks or status aggregation. `agent/runner.py` defines a plugin interface for future Python checks and continues after a plugin exception. The existing Bash allowlist remains in place for unattended safety.

## Paths, persistence, and use

During automatic ISO boot, `iso/runtime/select-report.sh` first approves RAM or a mounted labelled USB destination. The boot entry point then creates `/reports` as a live-root link to **that approved destination**. It refuses an unexpected existing `/reports` path. The launcher writes:

- `/reports/report.json` — structured report, fixed name.
- `/reports/report.txt` — technician-readable rendering of the same results, fixed name.
- `/reports/server-check-<identity>-<UTC>-<random>.txt` — existing unique raw report, retained for exact evidence and prior workflows.

The Python writer stages each fixed report in the same directory and replaces it after a complete write. New files have mode `0600`. The optical ISO remains read-only. The fixed names represent the latest run in that report destination; the uniquely named raw report preserves earlier local runs. Do not reboot while the only report copy is in RAM.

Outside the ISO, `server-check.sh` writes structured files next to its selected raw report. To request the literal `/reports` directory on a Linux host, choose it explicitly only after confirming that it is a safe RAM or approved USB destination:

```bash
sudo ./server-check.sh --mode auto --output-dir /reports
```

The default `REPORT_FORMAT=both` writes JSON and text. `--set REPORT_FORMAT=text` retains the prior raw-text-only behavior when Python is intentionally unavailable. Structured reporting requires `python3`; failure to create both fixed report files returns toolkit exit code `3`. Diagnostic results still use `0` for PASS, `1` for WARN, and `2` for FAIL.

Examples generated by the production renderer are in [example JSON](../examples/report.json) and [example text](../examples/report.txt). They contain synthetic hardware information. Regenerate them with `python3 examples/generate.py`.

## File structure and implementation steps

| Path | Role |
| --- | --- |
| `src/server_check/reporting/model.py` | Typed check/report contract and aggregation. |
| `src/server_check/reporting/render.py` | JSON and text views. |
| `src/server_check/reporting/writer.py` | Atomic local output and transport sink protocol. |
| `src/server_check/reporting/legacy.py` | Adapter for existing Bash evidence and verdicts. |
| `src/server_check/reporting/__main__.py` | Launcher-facing conversion command. |
| `src/server_check/agent/runner.py` | Optional future Python check plugin runner. |
| `tests/test_reporting.py` | Contract, aggregation, mapping, sink, CLI, and plugin tests. |
| `examples/` | Generated synthetic JSON/text reports. |

The increment was implemented in this order: define the model and status policy; add renderers and a sink; adapt completed Bash sections; wire the launcher and ISO's approved `/reports` alias; add the Python runtime to the ISO; test each mapping and output path. A future increment can migrate Bash checks one at a time to the Python plugin contract. Remote upload and Redfish orchestration are separate work.

## Current limitations

The ISO has not been rebuilt or booted with Python reporting on a physical Linux server in this workspace. `/reports` alias behavior, Python package inclusion, report permissions, and persistence on real USB media need a Debian build and boot test. The old Python inventory CLI still has its original stdout schema; it is not the unattended health-report entry point. Fixed-name `report.json` and `report.txt` are replaced by each completed run in the same destination.
